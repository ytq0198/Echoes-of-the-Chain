## 1. 先记住一句话

> ChainGrade 的重点不是把成绩“存进区块链”，而是让一条成绩能够可信地解释：谁签发、谁复核、谁能看、如何纠错、如何验证，以及系统故障后是否仍然一致。

如果老师只给一分钟，可以这样回答：

> 课程题目要求实现成绩信息存证与查询。我们认为直接把成绩明文或裸哈希写上链仍然不够：成绩是敏感且低熵的数据，错误成绩也可能被不可篡改地保存，现实中还必须允许申诉和修订。因此我们用 Hyperledger Fabric 实现了教师签发、独立复核、学生本人持有和外部验证的完整生命周期。公共账本只保存状态和带随机盐的详情承诺，成绩明文进入私有数据集合；修订不覆盖旧记录，而是让旧版本变为 `SUPERSEDED`、新版本经独立复核后变为 `ACTIVE`。最终系统还支持原子 CSV 批量导入、有限字段授权和可携带 VC，并用 120 项项目测试、84 个正式性能单元和故障恢复探针验证实现。

这段话包含项目的四个核心判断：

1. 上链不等于可信，可信来自身份、职责分离和状态规则；
2. 隐私不能依靠“别人猜不到哈希”，需要随机盐和私有集合；
3. 不可篡改不等于永远不能纠错，正确方式是保留旧版本并产生新版本；
4. VC 文件的签名只证明文件未被修改，当前是否有效仍要查询链上状态和锚定关系。

## 2. 汇报时的完整叙事主线

建议不要按“我们先写了前端、再写了后端”讲。老师更容易理解的顺序是：

```text
课程要求
  ↓
普通成绩上链存在三个矛盾
  ↓
把矛盾转化为系统约束
  ↓
用 Fabric 身份、私有数据和状态机实现约束
  ↓
用浏览器工作台形成完整业务闭环
  ↓
用功能、负向、性能和故障证据验证主张
  ↓
说明当前边界和下一步
```

汇报时反复围绕下面三个矛盾展开，七阶段能力演进只作为过程证据，不要喧宾夺主。

| 核心矛盾 | 仅做普通 Demo 会怎样 | ChainGrade 的解决方式 |
| --- | --- | --- |
| 管理方便与结果可信 | 一个管理员既录入又确认，错误和越权都能进入账本 | issuer/reviewer 使用不同证书属性；提交人不能自审；链码约束状态转换 |
| 验证需求与隐私保护 | 明文上链永久泄露；成绩裸哈希可枚举 | 随机盐 + 确定性 JSON + 公共 `detailHash` + Fabric 私有数据集合 |
| 不可篡改与现实纠错 | 覆盖会丢失历史；完全禁止修改又不符合教务流程 | 新建修订版本；旧版本 `SUPERSEDED`，新版本重新复核后 `ACTIVE` |

## 3. 项目解决的真实问题

### 3.1 为什么“成绩上链”仍然可能不可信

区块链能够证明某条记录从写入后没有被某个数据库管理员静默覆盖，但不能自动证明写入时的数据正确。如果同一人可以录入和批准，那么错误成绩只会变成“不可篡改的错误”。因此系统必须回答：

- 调用者属于哪个组织、拥有什么角色；
- 草稿由谁提交，复核是否来自另一身份；
- 当前状态能否执行这个操作；
- 每次状态变化是否保留交易号、时间和操作者摘要。

ChainGrade 把这些规则放在链码中，而不是只放在前端按钮或 API 判断中。前端和 API 可以改善用户体验，但最终安全边界是所有 Peer 都会执行的链码。

### 3.2 为什么成绩裸哈希仍然不安全

成绩通常只有 0–100 分或少量等级。假设公共账本保存 `SHA256(score)`，攻击者只需计算 101 次就能建立对应表。即便把课程名一起哈希，只要课程集合较小，仍可离线枚举。

本项目把私有详情规范化后计算承诺：

$$
detailHash=SHA256(canonicalJSON(courseName,score,grade,salt,schemaVersion)).
$$

其中 `salt` 是私有随机盐，不进入公共账本。公共侧只能看到 `detailHash`，私有侧才保存课程名、分数、等级和盐值。这样公开验证者可以检查持有者给出的详情是否匹配承诺，却不能只靠枚举 0–100 分恢复成绩。

### 3.3 为什么纠错不能使用覆盖更新

如果直接把 85 分覆盖成 95 分，系统无法回答“谁在什么时候基于什么流程改了成绩”；如果把链上成绩设计成永远不能变化，又无法处理录入错误、复核争议和申诉。

本项目把“不可篡改”解释为历史不能被抹掉，而不是业务状态永远不变：

```text
旧凭证 ACTIVE
   │ 教师创建新草稿，记录 previousCredentialId
   ▼
新凭证 PENDING_REVIEW，旧凭证仍 ACTIVE
   │ 独立 reviewer 复核通过，同一笔交易完成切换
   ▼
旧凭证 SUPERSEDED + 新凭证 ACTIVE
```

这样既不会让未经批准的新成绩提前生效，也不会出现两个版本同时有效。

## 4. 总体架构与各层职责

### 4.1 运行架构

```text
教师 / 复核员 / 学生 / 外部验证者
                 │
                 ▼
          Vue 3 浏览器界面
                 │ 同源 HTTP、Cookie、CSRF
                 ▼
          Fastify TypeScript API
                 │ Fabric Gateway
                 ▼
      Org1 Peer ── grade 链码 ── Org2 Peer
           │                         │
           ├── 公共状态与承诺       └── 同一通道账本副本
           └── Org1 隐式私有集合
                 ▲
              Raft Orderer
```

课程环境使用一个 Raft Orderer、两个 Peer 和一个 Node.js Chaincode-as-a-Service 进程。它足以验证多 Peer 一致性、身份权限和故障恢复，但单 Orderer 不具备写入高可用，答辩时必须主动说明这一边界。

### 4.2 为什么选择 Hyperledger Fabric

这个场景的参与者不是匿名公网用户，而是学校、院系、教师、学生和验证机构。它们需要身份与权限，而不是 Token 激励。Fabric 与需求的对应关系如下：

| Fabric 能力 | 在本项目中的作用 | 不应夸大的地方 |
| --- | --- | --- |
| MSP 与 X.509 属性 | 表示组织和 `app.role`、`subject.hash` | 证书本身不能保证业务数据正确 |
| 链码 | 统一执行状态机、职责分离和哈希校验 | 不能代替所有应用层输入校验 |
| Private Data Collection | 让成绩明文不向整个通道广播 | 授权组织自身仍能访问其私有数据 |
| 公共账本与历史 | 保存状态、承诺、交易号和版本关系 | 不适合存放姓名、学号、申诉正文 |
| 背书、排序和提交 | 让多个节点得到一致的状态变更 | 当前单 Orderer 不是生产高可用拓扑 |

### 4.3 为什么采用 B/S 架构

老师可能问“为什么不用让学生直接连接 Fabric？”回答是：终端用户不应管理节点证书、Gateway 连接和私钥。浏览器负责操作体验，API 管理会话和受控 Gateway 身份，链码负责最终规则。三层的职责不能混淆：

- Web：表单、CSV 本地预检、角色工作台、状态和错误提示；
- API：Schema 再校验、Cookie/CSRF、规范化与哈希、Gateway 调用、错误码翻译；
- Chaincode：证书属性、组织约束、状态机、原子读写和私有数据承诺。

### 4.4 Fabric 网络结构与代码原理

这一节是代码答辩的网络层主线。不要只画“前端—后端—区块链”三个框，而要说明节点由什么脚本启动、各自保存什么、一次交易如何从 API 到两个 Peer，以及当前拓扑究竟证明了什么。

#### 4.4.1 逻辑拓扑和物理进程

```text
                                         ┌────────────────────────────┐
                                         │ orderer.example.com        │
                                         │ OrdererMSP / Raft          │
                                         │ 7050 排序  7053 管理       │
                                         └─────────────┬──────────────┘
                                                       │ 生成区块并分发
                         ┌─────────────────────────────┴─────────────────────────────┐
                         ▼                                                           ▼
┌─────────────────────────────────────────┐                    ┌─────────────────────────────────────────┐
│ peer0.org1.example.com                  │                    │ peer0.org2.example.com                  │
│ Org1MSP                                 │                    │ Org2MSP                                 │
│ 7051 Peer gRPC / 7052 链码服务 / 9444 运维 │                  │ 9051 Peer gRPC / 9052 链码服务 / 9445 运维 │
│ 公共账本 + Org1 隐式私有集合明文       │                    │ 公共账本 + Org1 私有数据哈希           │
└───────────────┬─────────────────────────┘                    └───────────────┬─────────────────────────┘
                │ Gateway 连接                                                │ 链码生命周期安装/批准
                └───────────────────────┬─────────────────────────────────────┘

                              ┌────────────────────┐
                              │ grade CCaaS        │
                              │ Node.js / 9999     │
                              │ package ID 绑定    │

                                        ▲
                                        │ TLS gRPC + actor 证书签名
                              ┌────────────────────┐
                              │ Fastify API        │
                              │ Fabric Gateway SDK │

```

当前所有业务 Gateway 都连接 `peer0.org1:7051`，但 issuer、reviewer、student 使用三套不同的 Org1 客户端证书和私钥。Org2 Peer 不直接承载浏览器用户身份，而是保存同一通道的第二份公共账本、参与链码生命周期，并用于一致性和恢复实验。

| 进程/对象 | 身份 | 端口或位置 | 实际职责 |
| --- | --- | --- | --- |
| Orderer | `OrdererMSP` | 7050；管理端 7053；运维端 9443 | 接收已背书交易、排序、组成区块；不执行成绩链码 |
| Org1 Peer | `Org1MSP` | 7051；Peer 链码服务端 7052；运维端 9444 | 接收 Gateway 提案、模拟和背书；保存公共状态及 Org1 私有详情 |
| Org2 Peer | `Org2MSP` | 9051；Peer 链码服务端 9052；运维端 9445 | 保存公共账本副本、验证区块、参与链码生命周期和恢复核验 |
| grade CCaaS | 链码 package ID | 127.0.0.1:9999 | 独立 Node.js 进程执行 `grade` 合约；实验拓扑中两个 Peer 连接同一服务实例 |
| 通道 | `chaingrade` | 通道配置块 | 隔离本项目账本和链码定义 |
| 链码定义 | `grade` 0.9 sequence 1 | 两组织批准后提交 | 绑定名称、版本、序号、包与背书策略 |

#### 4.4.2 两种启动路径为什么都存在

项目保留两条网络启动路径，但它们使用同一套 Fabric 2.5.16 语义，不是“真链”和“假链”两套业务实现。

| 路径 | 入口代码 | 作用 | 使用场景 |
| --- | --- | --- | --- |
| 标准容器路径 | `infra/fabric/network.sh` | 包装 Fabric 官方 test-network，使用 CA、Docker、LevelDB 建立双组织网络 | 初始开发和 Docker 正常环境 |
| 原生进程路径 | `infra/fabric-native/native-network.sh`、`deploy-chaincode.sh` | 使用已经固定版本的 `peer`、`orderer`、`configtxgen`、`osnadmin` 二进制直接运行 | 学校服务器 Docker 存储故障后的可恢复运行路径 |

标准路径的 `network.sh up` 实际调用官方脚本：

```bash
./network.sh up createChannel -ca -s leveldb \
  -c chaingrade -i 2.5.16 -cai 1.5.17
```

它创建 Org1、Org2、Orderer 的 MSP/TLS 材料和 `chaingrade` 通道，然后调用 `enroll-identities.sh` 注册三类业务证书。`bootstrap.sh` 将 Fabric、Fabric CA、fabric-samples commit 和 jq 都锁定到 `versions.env`，下载内容进入 `.tools`，不会依赖服务器碰巧安装的系统版本。

原生路径产生的仍是真实 Fabric 区块、背书、排序和 Peer 世界状态，只是不通过 Docker 管理进程。它复用已经生成的 MSP/TLS 材料，把账本、WAL、快照、PID 和日志放进 `.runtime/native-fabric`。`.tools` 和 `.runtime` 都不进入 Git 或提交包。

#### 4.4.3 原生网络怎样建立通道

`native-network.sh up` 按以下顺序工作：

1. `preflight.sh` 检查 `peer`、`orderer`、`osnadmin`、`configtxgen` 是否存在，证书是否至少再有效 24 小时，所需端口和 10 GiB 磁盘空间是否满足；
2. `prepare_channel_block` 把官方 `configtx.yaml` 中的容器主机名改成 localhost；
3. `configtxgen -profile ChannelUsingRaft` 生成 `chaingrade.block`；
4. 启动单个 Raft Orderer，启用 channel participation API；
5. 用 `osnadmin channel join` 让 Orderer 加入 `chaingrade`；
6. 分别启动 Org1 Peer 和 Org2 Peer；
7. 使用两组织管理员 MSP 执行 `peer channel join -b chaingrade.block`；
8. `status` 只检查受管 PID，随后还需要账本和读写探针判断业务是否恢复。

关键代码位置：

| 文件与行段 | 做了什么 | 为什么需要 |
| --- | --- | --- |
| `native-network.sh:41–54` | 生成本机可用的 Raft 通道块 | 容器 DNS 名称在原生进程模式下不可解析 |
| `native-network.sh:56–105` | 配置 TLS、MSP、WAL/快照并启动 Orderer | 把排序服务的数据目录限制在项目运行区 |
| `native-network.sh:107–146` | 参数化启动两个 Peer | 同一函数避免 Org1/Org2 配置漂移 |
| `native-network.sh:148–162` | 以各组织管理员身份加入通道 | Peer 启动不等于已经拥有该通道账本 |
| `native-network.sh:200–209` | 严格控制启动顺序 | 先有通道和排序服务，再启动并加入 Peer |

#### 4.4.4 三类业务身份如何进入证书

`infra/fabric/enroll-identities.sh` 连接 Org1 CA，在开发网络中注册并登记：

```text
cgissuer   → app.role=issuer
cgreviewer → app.role=reviewer
cgstudent  → app.role=student, subject.hash=<demo student hash>
```

属性使用 `:ecert` 写入登记证书。最终 MSP 目录分别是：

```text
.../users/ChaingradeIssuer@org1.example.com/msp
.../users/ChaingradeReviewer@org1.example.com/msp
.../users/ChaingradeStudent@org1.example.com/msp
```

API 的 `fabric-config.ts` 只保存这些目录位置，不把证书和私钥复制到源码。`FabricCredentialLedger.newIdentity()` 从 `signcerts` 读取证书，`newSigner()` 从 `keystore` 读取私钥并建立签名器。

“独立复核”的准确含义是 issuer 与 reviewer 是两张不同证书、不同 `app.role` 的独立应用身份，链码还比较提交者和复核者身份摘要。当前二者都属于 `Org1MSP`，所以这不是“跨组织复核”。如果要实现跨院系或跨学校复核，应把 reviewer 身份放到独立 MSP，并把背书策略改为同时要求相关组织。

#### 4.4.5 链码为什么采用 CCaaS，以及如何部署

Docker 受损时，传统“Peer 构建并启动链码容器”的方式不可用。项目采用 Chaincode-as-a-Service（CCaaS），让 `grade` 合约作为可管理的 Node.js 进程运行。

`deploy-chaincode.sh` 的生命周期是：

```text
生成 connection.json(address=127.0.0.1:9999)
  → 生成 metadata.json(type=ccaas)
  → 以固定排序/时间/owner 打包，保证 package ID 可重复
  → calculatepackageid
  → 在 Org1、Org2 Peer 分别 install
  → 编译 TypeScript，使用 package ID 启动 fabric-chaincode-node server
  → Org1、Org2 分别 approveformyorg
  → commit 链码定义，并同时指定两个 Peer 地址
  → querycommitted 核对 version=0.9、sequence=1
```

这里必须区分三个概念：

- **安装 package**：让某个 Peer 知道如何连接该链码服务；
- **组织批准 definition**：组织同意名称、版本、序号和策略；
- **提交 definition**：把各方认可的链码定义写入通道配置，使 `grade` 可被调用。

`start` 与 `deploy` 也不同：首次安装/升级使用 `deploy`；账本重启后使用 `start`，它要求包已安装、定义已提交，只重新启动 CCaaS，不重复提交链码生命周期交易。

#### 4.4.6 当前背书策略到底保证什么

开发网络的策略是：

```text
OR('Org1MSP.peer','Org2MSP.peer')
```

它表示 Org1 或 Org2 的一个合法 Peer 背书即可满足策略，不是“双组织必须共同签字”。API Gateway 当前连接 Org1 Peer，而成绩详情写入 Org1 隐式私有集合，因此普通业务交易通常由 Org1 Peer 模拟和背书。Org2 从区块中获得公共写集与私有数据哈希，不获得 Org1 私有成绩明文。

选择 `OR` 的原因是课程开发拓扑只有 Org1 持有该隐式集合的详情，强制 Org2 同时模拟包含 Org1 私有数据的写入会与隐私分发边界冲突。它能证明 Peer 验证和账本复制，但不能证明“每条成绩都经过两个组织共同背书”。生产化可按业务记录使用状态级背书，或设计双方都能验证但不获得成绩明文的多组织承诺流程。

还要区分背书和复核：

- Fabric **背书**是节点对链码模拟结果签名；
- 业务 **复核**是 reviewer 身份调用 `ApproveCredential` 改变成绩状态。

当前 reviewer 的业务批准是一笔新的链上交易，不等同于 Org2 Peer 的 Fabric 背书。

#### 4.4.7 一笔写交易完整经过哪些步骤

以教师创建成绩草稿为例：

1. 浏览器向 Fastify API 提交请求，Cookie 证明会话，CSRF Token 和 Origin 防止跨站伪造；
2. API 校验 Schema，把成绩详情确定性序列化并计算 `detailHash`；
3. `FabricCredentialLedger.contractFor('issuer')` 选择 issuer MSP；若已有连接则复用角色连接；
4. `newGrpcClient()` 使用 Org1 Peer TLS 根证书连接 `localhost:7051`，并以 `peer0.org1.example.com` 作为证书主机别名验证；
5. Gateway 用 issuer 证书和私钥对提案签名，公共草稿进入 arguments，成绩详情进入 transient data；
6. Org1 Peer 调用 9999 上的 CCaaS 模拟 `CreateCredentialDraft`，链码检查 `app.role`、状态、ID 和详情承诺，形成公共/私有读写集并背书；
7. Gateway 将已背书交易提交到 Orderer；Orderer 不理解成绩业务，只负责排序和组成区块；
8. 两个 Peer 接收区块，验证背书策略与 MVCC 版本：有效交易更新公共账本，Org1 还提交私有详情，Org2 只保存对应私有哈希；
9. API 等待 commit status，再向浏览器返回成功。收到 HTTP 201 时不是“已发送”，而是当前 Gateway 已确认提交结果。

代码中的超时分层为：查询 5 秒、背书 30 秒、向排序服务提交 10 秒、等待提交状态 60 秒。这样慢背书、排序失败和提交超时能被区分，而不是无限挂起。

#### 4.4.8 查询为什么不经过 Orderer

`evaluateTransaction` 只在连接的 Peer 上模拟查询并返回结果，不产生区块，也不经过 Orderer；`submit`/`submitTransaction` 才走背书、排序和提交路径。因此：

- 公开验真和列表查询可以在 Orderer 暂停时从已有 Peer 状态继续读取；
- 创建、批准、撤销和消费授权等写操作需要 Orderer；
- 单 Peer 查询只反映该 Peer 已提交的状态，高可信验证可比较多个 Peer 或等待区块同步。

项目的 `ledger-info.sh` 分别以 Org1 和 Org2 管理员上下文调用 `peer channel getinfo -c chaingrade`，比较 `height`、`currentBlockHash` 和 `previousBlockHash`。字符串完全一致才返回 `consistent=true`。这比只检查两个 Peer 进程存活更能说明账本是否同步。

#### 4.4.9 网络状态存放在哪里，如何避免污染仓库

| 路径 | 内容 | 是否进入 Git |
| --- | --- | --- |
| `.tools/fabric-samples` | 固定版本二进制、配置、开发 MSP/TLS 材料 | 否 |
| `.runtime/native-fabric/data` | Orderer 账本/WAL/快照和 Peer 世界状态/区块 | 否 |
| `.runtime/native-fabric/channel` | 本机通道配置块 | 否 |
| `.runtime/native-fabric/pids`、`logs` | 受管进程 PID 和诊断日志 | 否 |
| `infra/fabric*` | 可复现的脚本和版本声明 | 是 |

冷备份脚本先停止 CCaaS、Peer 和 Orderer，使磁盘状态静止，再生成归档和 SHA-256。备份包含 MSP 私钥，因此保存在仓库外并设置 `0600`。恢复脚本要求显式 `--confirm-restore`，并把原运行目录移动为带时间戳的 `pre-restore` 目录，而不是直接删除，便于失败回退。

#### 4.4.10 当前网络结构的证据边界

当前拓扑能够证明：

- 真实 Fabric 2.5.16 的证书、背书、排序、区块提交和私有集合能够运行；
- Org1、Org2 Peer 可以维持一致的公共账本；
- 业务角色由独立证书属性约束，而不是由前端下拉框决定；
- Peer、CCaaS、Orderer 故障后可以按探针判据恢复。

当前拓扑不能证明：

- 每笔成绩经过两个组织共同背书；
- reviewer 属于独立院系/学校 MSP；
- 单 Orderer 故障时写入不中断；
- 单个 9999 CCaaS 服务实例故障时链码无感切换；
- WSL 回环性能等于跨主机生产性能。

## 5. 数据模型与隐私原理

### 5.1 公共状态和私有详情

| 数据 | 公共账本 | 私有集合或受控端 | 原因 |
| --- | --- | --- | --- |
| 凭证 ID、状态、版本 | 是 | 可缓存 | 外部验真和审计需要 |
| 学生匿名哈希、课程哈希 | 是 | 是 | 用于索引和主体关联，不直接出现姓名学号 |
| `detailHash` | 是 | 可重算 | 证明提交的详情与链上承诺一致 |
| 课程名、分数、等级 | 否 | 是 | 成绩明文属于敏感数据 |
| 随机盐 | 否 | 是 | 阻止低熵枚举 |
| 申诉正文、决定理由 | 否 | 是 | 争议信息不应扩散到全通道 |
| 分享 Token 明文 | 否 | 创建时返回一次 | 泄漏后可能形成越权能力 |

链码的 `CreateCredentialDraft` 接收公共草稿参数，并从 transient data 中读取 `gradeDetails`。链码重算并比较 `detailHash`，匹配后才把公共记录写入世界状态、把详情写入 `_implicit_org_<MSPID>`。transient data 不进入区块交易正文，只被本次背书所需节点处理。

### 5.2 为什么需要确定性序列化

JSON 对象的键顺序和空白形式可能不同：`{"a":1,"b":2}` 与 `{"b":2,"a":1}` 语义相同，但直接对原始字符串哈希会得到不同结果。API 中的 `canonicalJson` 固定链上详情承诺的字节表示；标准 VC 签名则使用独立的 RFC 8785 JCS 实现。两者用途不同，不应混为一个函数：

- `apps/api/src/lib/canonical-json.ts`：服务于已有链上 `detailHash` 协议；
- `packages/shared/src/vc/canonicalize.ts`：服务于 VC 文件的跨实现签名字节。

保留两个明确版本的规范化器，能够避免后续升级 VC 标准时意外改变历史链上承诺。

### 5.3 学生身份如何绑定

学生证书包含：

```text
app.role=student
subject.hash=<64 位主体哈希>
```

学生读取私有成绩或提交申诉时，链码比较证书中的 `subject.hash` 与凭证记录的 `subjectHash`。`ReadMyCredentialPrivate` 和 `SubmitAppeal` 都在链码层执行这一比较，因此把前端 URL 改成别人的凭证 ID 也无法读取详情。

## 6. 身份、权限与会话安全

### 6.1 双层授权

系统同时存在应用会话和 Fabric 身份，但二者作用不同：

| 层次 | 解决什么问题 | 典型实现 |
| --- | --- | --- |
| API 会话 | 谁能进入哪个工作台，尽早返回 401/403 | HMAC 签名 Cookie、角色 Claim、CSRF Token |
| Fabric 身份 | 谁能真正执行链上交易 | `app.role`、MSP、`subject.hash`、链码检查 |

API 的 `SessionService` 使用 HMAC-SHA256 签名会话载荷；Cookie 设置 `HttpOnly` 和 `SameSite=Strict`，写操作还检查精确 Origin 和 `x-csrf-token`。密码只从运行时环境变量读取，不写进仓库。

必须强调：API 角色检查不是唯一防线。链码中的 `assertRole()` 会读取调用证书的 `app.role`；`ApproveCredential` 还比较提交者和复核者身份摘要，拒绝同一身份自审。

### 6.2 四类角色

| 角色 | 能做什么 | 明确不能做什么 |
| --- | --- | --- |
| issuer 教师 | 创建单条/批量草稿、发起修订、查看本人提交 | 不能批准自己的草稿，不能读取任意学生私有详情 |
| reviewer 复核员 | 批准、驳回、撤销、处理申诉 | 不能直接通过“接受申诉”修改成绩 |
| student 学生 | 查看本人凭证与私有详情、申诉、创建披露授权、导出 VC | 不能读取其他学生成绩，不能改变凭证状态 |
| external verifier 外部验证者 | 公开状态验证、验证 VC、消费有效授权 | 默认不能看到成绩明文，也不持有 Fabric 私钥 |

## 7. 两套状态机为什么这样设计

### 7.1 凭证状态机

```text
PENDING_REVIEW ──批准──> ACTIVE ──撤销──> REVOKED
      │                    │
      └──驳回──> REJECTED  └──新版批准──> SUPERSEDED
```

五个状态的含义：

- `PENDING_REVIEW`：教师已提交但未独立确认；
- `ACTIVE`：当前有效，可供学生持有和外部验证；
- `REJECTED`：草稿没有通过复核，从未成为有效成绩；
- `REVOKED`：曾经有效，但由于撤销决定不再有效；
- `SUPERSEDED`：曾经有效，后来被一个新版本取代。

`REJECTED`、`REVOKED` 和 `SUPERSEDED` 不能合并为一个“无效”状态，因为它们回答的审计问题不同：没有通过、后来撤销、还是正常修订。

链码 `ApproveCredential` 在批准修订版时，先确认旧版本仍为 `ACTIVE`。若旧版本已经变化，返回 `STALE_AMENDMENT`；否则在同一笔 Fabric 交易中把旧版本改为 `SUPERSEDED`、新版本改为 `ACTIVE`。同一交易失败时两项写入一起回滚。

### 7.2 申诉状态机

```text
OPEN ──接受──> RESOLVED_ACCEPTED
  └──驳回──> RESOLVED_REJECTED
```

最重要的设计点是：`RESOLVED_ACCEPTED` 不会直接修改成绩。它只说明复核员认可“应该进入更正流程”。之后仍需教师创建修订草稿，并由独立 reviewer 复核。

如果接受申诉就直接改成绩，reviewer 会获得绕过 issuer 的修改能力，破坏职责分离。这是答辩中非常值得主动讲出的设计原因。

## 8. 核心代码原理

### 8.1 单条签发：先验证承诺，再分区写入

对应代码：`chaincode/grade-contract/src/grade-contract.ts` 的 `CreateCredentialDraft`，以及 `apps/api/src/ledger/fabric-ledger.ts` 的 `createDraft`。

关键控制流：

```text
API 规范化私有详情并计算 detailHash
  → Gateway 把公共参数放 arguments、私有详情放 transientData
  → 链码检查 issuer 角色和 credentialId 唯一性
  → 链码重算 transient 数据哈希
  → 写公共 PENDING_REVIEW 记录
  → 写签发组织隐式私有集合
```

链码不会相信 API 声称的 `detailHash`；它必须对收到的 transient 字节重新计算。这样即使 API 编排出错，公共承诺和私有详情也不会悄悄不一致。

### 8.2 独立复核：链码而非界面保证不能自审

对应代码：`ApproveCredential` 和 `assertRole`。

核心判断可概括为：

```ts
assertRole(ctx, 'reviewer');
if (record.status !== 'PENDING_REVIEW') reject();
if (record.submittedByIdentityHash === identityHash(ctx)) reject();
```

实际代码还检查组织归属和修订前序状态。页面隐藏按钮只是交互优化，真正的不可绕过约束是证书属性和链码状态机。

### 8.3 CSV 批量原子性：不是 API 循环

对应代码：

- `packages/shared/src/grade-csv.ts`：CSV 解析；
- `apps/api/src/routes/credentials.ts`：API 规范化与请求编排；
- `apps/api/src/ledger/fabric-ledger.ts`：一次提交 `CreateCredentialBatch`；
- `chaincode/grade-contract/src/grade-contract.ts`：全批预检后写入。

`CreateCredentialBatch` 的关键是“先完成所有检查，再开始任何写入”：

1. 检查 1–50 条上限；
2. 检查批内 ID 是否重复；
3. 检查账本中是否已存在 ID；
4. 检查每条私有详情是否存在、Base64 是否合法；
5. 重算每条详情哈希；
6. 检查 transient 中没有多余条目；
7. 所有检查通过后才循环写公共和私有状态。

所有记录使用同一个 `ctx.stub.getTxID()`。若任意一条冲突，整笔 Fabric 交易无效，不会出现“成功一半”的班级成绩。前端仍可逐行提示格式错误，但链上提交是全有或全无。

### 8.4 修订：固定主体和课程，不让修订变成换人换课

`CreateAmendmentDraft` 从旧凭证继承并核对 `subjectHash` 与 `courseHash`。如果新草稿试图改变学生主体或课程身份，链码返回 `IMMUTABLE_IDENTITY`。新记录保存 `previousCredentialId` 和递增版本号。

这项检查的意义是：修订只能纠正同一学生、同一课程的内容；如果要为另一个学生或另一门课签发，应创建新的凭证，而不是伪装成修订。

### 8.5 学生查询：证书属性与记录主体双向匹配

`ReadMyCredentialPrivate` 先检查 `app.role=student`，再检查组织，最后比较证书 `subject.hash` 与记录 `subjectHash`。通过后才从签发组织的隐式私有集合读取详情。缺少私有数据会返回明确错误，而不是返回空成绩造成误解。

### 8.6 有限字段披露：链上保存授权状态，不保存 Token 明文

学生选择 `courseName`、`score`、`grade` 中的字段，并设置用途、验证者、过期时间和最多使用次数。API 生成 32 字节随机 Token，只把 Token 哈希写入链上；Token 明文仅在创建响应返回一次。

消费时，链码校验 Token、用途、验证者、状态、过期时间和剩余次数，并原子增加 `usedCount`。API 先评估可披露内容，再提交消费交易；成功后才返回选定字段。

边界必须说清楚：这是 bearer capability 加字段级授权，不是 BBS+ selective disclosure，也不是零知识证明。验证者看到字段后仍可保存，Token 被转发也存在风险。

### 8.7 可携带 VC：签名、状态和锚定三段联合验证

对应代码：

- `apps/api/src/vc/exporter.ts`：从链上公共记录和学生私有详情构造 VC；
- `apps/api/src/vc/signer.ts`：JCS 规范化后使用 Ed25519 签名；
- `apps/api/src/vc/verifier.ts`：联合验证；
- `packages/shared/src/vc/schema.ts`：文件结构约束。

验证结论不是“签名正确就通过”，而是同时要求：

```text
文件 Schema 合法
∧ 使用系统信任的签发者公钥
∧ Ed25519 签名正确
∧ 链上当前状态为 ACTIVE
∧ 文件 detailHash 与链上记录一致
∧ 文件 subjectHash 与链上记录一致
= valid
```

签名回答“文件自签发后有没有被改”；链上状态回答“现在还是否有效”；锚定回答“文件描述的是不是这条链上记录”。三者缺一不可。`REVOKED`、`SUPERSEDED`、详情锚定错误、主体锚定错误或文件篡改都会得到 `invalid`。

## 9. 前端设计如何服务业务，而不只是美化

界面分为教师签发、独立复核、学生凭证和公开验真四个工作台。设计目标不是显示尽可能多的数据，而是让用户在每一步看懂：

- 当前处于什么状态；
- 下一步由哪个角色处理；
- 哪些字段在公共账本，哪些是私有数据；
- 操作失败是未登录、角色错误、状态冲突还是验证失败；
- 手机端是否仍可完成主要任务。

系统使用统一纸张色背景、深绿色信任色、金色章节标记、衬线大标题和无衬线正文。大型字体只用于角色和结果，不用于哈希、表格和说明文字。最终在 1536×1024、1440×900、1280×720 和 390×844 四种视口验收，无横向溢出，浏览器 console warning/error 为 0。

## 10. 工程证据：每个主张如何被证明

不要只说“有 120 个测试”。答辩时使用“主张—机制—证据”的方式。

| 主张 | 实现机制 | 直接证据 | 能支持的结论 |
| --- | --- | --- | --- |
| 职责分离 | issuer/reviewer 不同证书属性；提交身份摘要不能等于复核身份摘要 | 真实 issuer 创建、reviewer 批准；错误角色返回 403；链码负向测试 | 角色不能通过界面或 API 参数互换 |
| 私有成绩不进公共账本 | transient data + 隐式私有集合 + 公共哈希承诺 | 隐私检查脚本、学生本人查询、公开验真响应不含成绩 | 当前实现的公共记录不含成绩明文 |
| 修订保留历史 | `previousCredentialId`、版本号、`SUPERSEDED` | 新旧状态测试与链上查询 | 旧版本没有被覆盖，新版本需重新复核 |
| 批量原子性 | 一次 `CreateCredentialBatch` 交易，全批预检后写入 | 冲突批次 HTTP 409；原本合法的新 ID 随后查询仍为 404 | 冲突不会造成部分写入 |
| VC 不是只验签 | 签名 + ACTIVE 状态 + detail/subject 锚定 | 篡改、REVOKED、SUPERSEDED、错误锚定负向测试 | 当前有效性由文件和账本共同决定 |
| 多 Peer 一致 | 同一通道账本与恢复后稳定探针 | 双 Peer 高度和区块哈希一致；全量账本审计 | 已测环境中两个 Peer 恢复到一致状态 |

### 10.2 性能实验如何解释

正式基准设计是：

```text
7 类负载 × 4 档并发 × 3 轮 = 84 个正式单元
每单元：10 秒预热 + 30 秒正式采样
并发：1 / 5 / 10 / 20
```

七类负载分别是 `public-verify`、`student-private`、`issue-review`、`batch-1`、`batch-10`、`batch-25`、`batch-50`。84 个正式单元中合法请求失败率均为 0%。主要结果：

| 负载 | 最高中位吞吐 | 对应并发 | 该点 P95 |
| --- | ---: | ---: | ---: |
| 公开验真 | 746.614 次/秒 | 20 | 38.202 ms |
| 学生私有查询 | 752.360 次/秒 | 20 | 38.096 ms |
| 签发并复核 | 33.883 次/秒 | 20 | 700.615 ms |
| 批量 50 条 | 482.549 条/秒 | 20 | 2,497.371 ms |

正确解释是：只读负载在并发 20 时接近平台；较大批次提高了“成绩条目/秒”，但增加了单批尾延迟。不能说“系统生产 TPS 达到 752”，因为实验发生在 WSL 单机回环环境，共享宿主资源，且当前网络只有一个 Orderer。

### 10.3 故障恢复如何解释

稳定恢复不是看到进程状态为 RUNNING，而是连续三次读写成功，并且两个 Peer 的高度和区块哈希一致。已有故障探针结果：

| 故障对象 | 稳定恢复时间 | 期间记录的错误 |
| --- | ---: | --- |
| Org2 Peer | 14.030 s | 无 |
| CCaaS 链码进程 | 16.870 s | `INTERNAL_ERROR` 44 次 |
| 单 Orderer | 22.482 s | `INTERNAL_ERROR` 20 次 |

全量 QSCC 审计覆盖高度 12–4315，记录有效交易 32,527、无效交易 27；27 条无效交易来自正式矩阵结束后的故障诊断，正式性能矩阵内无效交易为 0。这个数据能说明已记录账本可解释，不能证明任意生产故障下都无数据丢失。

## 11. 演示时推荐的操作顺序

### 11.1 演示前准备

1. 提前确认 Fabric、CCaaS、API、Web 均已启动；
2. 准备 issuer、reviewer、student 三个浏览器会话或使用无痕窗口切换；
3. 准备一个全新凭证 ID，避免重复数据导致 409；
4. 准备一份正确 CSV 和一份包含重复 ID 的冲突 CSV；
5. 准备一个 ACTIVE 凭证用于学生查询、VC 导出和公开验真；
6. 不在投屏中展示 `.runtime/private/preview.env` 或任何密码；
7. 演示失败时切换到报告截图和已录制视频，不临时修改账本。

### 11.2 8–12 分钟演示脚本

| 时间 | 操作 | 同时解释的设计点 |
| --- | --- | --- |
| 0:00–0:45 | 首页和系统状态 | 这是一个项目、一条业务链，不是四个独立 Demo |
| 0:45–2:00 | issuer 创建成绩草稿 | 明文走 transient/PDC，公共侧保存承诺，初始状态待复核 |
| 2:00–3:00 | reviewer 查看并批准 | 独立身份、看不到不必要明文、批准后才 ACTIVE |
| 3:00–4:00 | student 查询本人私有成绩 | `subject.hash` 绑定，别人凭证 ID 无法越权读取 |
| 4:00–5:00 | 公开验真/二维码 | 默认只返回状态和承诺匹配，不公开成绩 |
| 5:00–6:30 | 学生申诉，reviewer 接受 | 接受申诉不直接改分，只允许进入后续修订流程 |
| 6:30–7:30 | 展示修订版本关系 | 旧版本 `SUPERSEDED`，新版本需重新复核 |
| 7:30–8:30 | CSV 原子批量导入 | 前端逐行预检，链上一次交易，全批成功或失败 |
| 8:30–9:30 | VC 导出并验证 | 签名、链上状态和锚定联合决定结果 |
| 9:30–10:30 | 展示性能/故障证据 | 说明样本数、环境和证据边界 |

### 11.3 最值得现场展示的负向用例

如果时间只够一个负向用例，优先展示批量原子回滚：

1. 提交包含一个已存在 ID 和一个新 ID 的批次；
2. API 返回 409；
3. 查询原本合法的新 ID，仍返回 404；
4. 解释：如果只是 API 循环，新 ID 可能已经写入；现在没有写入，证明整批是同一 Fabric 交易。

第二优先是 VC 篡改：导出后修改成绩或 `detailHash`，签名段失败；再解释即便签名正确，若链上状态为 `REVOKED` 或 `SUPERSEDED`，最终结论仍为无效。

## 12. 项目亮点和创新点应该怎样表述

不要声称发明了新密码学算法。建议将贡献概括为三个工程设计：

### 12.1 可信生命周期，而不是单次存证

系统约束了“教师签发—独立复核—学生持有—外部验真—修订/申诉”的完整过程。创新点在于把真实教务职责和纠错需求转化为可执行的链上状态机，而不是增加更多页面。

### 12.2 面向低熵成绩的隐私承诺模型

成绩明文不进入公共账本；随机盐阻止简单枚举；公共 `detailHash` 支持完整性核验；Fabric 私有集合控制明文传播范围。这是一套对成绩数据特征有针对性的工程组合。

### 12.3 链上状态与可携带 VC 联合验证

VC 让学生可以导出和携带凭证，但签名不能表达凭证后来是否撤销或被新版本取代。因此系统把离线文件签名与在线链上状态、详情锚定组合为最终验证结论。

### 12.4 可作为补充亮点的两项设计

- CSV 在一次 Fabric 交易中提交，利用交易原子性解决“班级数据成功一半”；
- 接受申诉不直接改分，避免 reviewer 借申诉入口绕过 issuer 和独立复核。

## 13. 老师可能询问的问题与建议回答

### 13.1 选题与架构

**Q1：为什么成绩管理一定要用区块链，数据库不行吗？**  
A：如果系统只有一个完全可信的学校主体，带审计日志的数据库更简单。我们使用 Fabric 的前提是成绩签发、院系复核和外部验证由不同职责主体参与，需要共同维护一份不能由单个管理员静默覆盖的状态历史。我们的结论不是“区块链替代数据库”，而是把链用于跨职责共享的状态、承诺和审计，界面索引等可重建数据仍可放普通应用层。

**Q2：为什么不用以太坊或其他公链？**  
A：成绩参与方身份明确、数据敏感，也不需要 Token 激励。公链会增加隐私、费用和密钥管理成本。Fabric 提供 MSP、证书属性、私有数据和许可网络，更直接对应学校和院系场景。

**Q3：两个 Peer 算不算真正去中心化？**  
A：它证明了多节点一致和职责分离的最小实验拓扑，但不能代表生产联盟规模。当前只有一个 Orderer，写入不具备高可用。生产化需要多组织、多 Orderer Raft 集群、治理和证书生命周期管理。

**Q4：为什么一个项目同时面向课程和竞赛？**  
A：课程功能和竞赛完善共享同一数据模型、链码、API、Web 与账本。竞赛方向是在课程闭环上增强隐私、互操作和工程证据，而不是另写一套产品，因此答辩和竞赛口径不会分叉。

### 13.2 隐私与密码学

**Q5：`subjectHash` 会不会仍然泄漏学号？**  
A：如果直接计算 `SHA256(学号)`，学号空间有限，确实可枚举。当前实验使用匿名合成主体和证书绑定，没有把真实学号上链；生产方案应使用机构域分离的随机化标识、HMAC/密钥化映射或专门 DID，而不是裸学号哈希。

**Q6：有了 Private Data Collection，为什么还要 `detailHash`？**  
A：PDC 控制明文传播范围，`detailHash` 让公共状态能够承诺某一份私有详情，并支持外部持有者核对。一个解决“谁能看到”，另一个解决“提交的详情是否与链上记录一致”。

**Q7：随机盐放在哪里？泄漏会怎样？**  
A：盐与成绩详情一起保存在签发组织私有集合，不进入公共状态。若私有详情整体泄漏，盐不能继续保护该条记录，但公共账本本身不会帮助攻击者提前枚举。生产环境还需加强 PDC 成员、备份和密钥治理。

**Q8：为什么有限披露不是零知识证明？**  
A：当前方案是带字段、用途、验证者、期限和次数约束的 bearer token。验证者最终会看到授权字段，且 Token 被转发仍可能被滥用。BBS+ 或零知识证明可以证明某些属性或范围而不暴露原值，当前项目没有实现，因此我们明确不作该声明。

**Q9：哈希承诺能防止教师一开始写错吗？**  
A：不能。哈希只能证明详情没有被替换。录入正确性依赖独立复核、学生查看和申诉修订流程。这也是项目不把“上链”等同于“真实”的原因。

### 13.3 状态机与业务逻辑

**Q10：为什么 reviewer 接受申诉后不直接修改成绩？**  
A：直接修改会让 reviewer 绕过教师签发职责。接受只表示异议成立，之后必须由教师创建新版本，再由独立复核员批准。这样申诉流程不会变成隐藏的改分入口。

**Q11：为什么不删除错误成绩？**  
A：删除会失去审计历史。未通过草稿保留为 `REJECTED`，曾经有效但撤销的记录是 `REVOKED`，被新版本替代的是 `SUPERSEDED`。公开验证只把 `ACTIVE` 当作当前有效。

**Q12：修订期间哪个版本有效？**  
A：新草稿处于 `PENDING_REVIEW` 时旧版本继续 `ACTIVE`；新版本批准的同一笔交易才将旧版本改为 `SUPERSEDED`。这样不会因一个未经批准的修订造成有效成绩中断。

**Q13：两个修订草稿并发会怎样？**  
A：它们都引用同一个旧 `ACTIVE` 版本。第一个成功批准后旧版本变为 `SUPERSEDED`；第二个批准时发现前序不再 `ACTIVE`，返回 `STALE_AMENDMENT`。Fabric 读写集版本检查也会阻止冲突提交。

**Q14：为什么区分 `REVOKED` 和 `SUPERSEDED`？**  
A：撤销表示该凭证被取消且没有由此自动指向有效后继；取代表示正常版本演进，并有 `previousCredentialId` 关系。两者对外部验证者和审计人员的含义不同。

### 13.4 代码与原子性

**Q15：怎么证明批量导入不是在后端循环？**  
A：API 的 `createBatchDrafts` 只调用一次 `contract.submit('CreateCredentialBatch', ...)`；链码先构建 `prepared` 列表并验证全部记录，之后才写入。成功批次所有记录具有相同 transaction ID；冲突批次返回 409，原本合法的新 ID 仍为 404。

**Q16：链码循环写到一半抛错，前面的写入会不会留下？**  
A：Fabric 链码执行产生的是提案读写集，只有整笔交易通过背书、排序和验证才提交。链码异常使交易失败，已产生的临时写集不会部分提交。不过我们仍选择先全批预检，减少无效执行和让错误更可解释。

**Q17：为什么 transient 里还要 Base64？**  
A：批量 transient 需要把多条二进制详情放入一个 JSON 映射，Base64 提供确定的二进制到文本表示。链码检查编码可逆、条目数量和每条哈希，防止缺失、重复或额外私有条目。

**Q18：为什么时间不能直接用 `Date.now()`？**  
A：不同 Peer 的本地时间可能不同，会破坏确定性执行。链码使用 Fabric 交易时间戳，使背书节点对同一交易得到一致结果。API 和界面可以使用本地时间做展示，但不能决定链上状态。

**Q19：为什么 API 和链码都做校验？**  
A：API 校验用于快速、清晰地返回 400；链码校验是不能绕过的最终约束。只在 API 校验会让其他客户端或错误配置的 Gateway 绕过规则；只在链码校验则用户体验和错误定位较差。

### 13.5 VC 与验证

**Q20：VC 已有数字签名，为什么还要查链？**  
A：签名只能证明文件自签发后未修改，不能证明它后来有没有撤销或被取代。ChainGrade 同时检查 Ed25519 签名、链上 `ACTIVE` 状态和详情/主体锚定。

**Q21：验证时使用凭证文件自带的公钥安全吗？**  
A：不安全，攻击者可以重签篡改文件并附上自己的公钥。本项目使用系统配置的受信任签发者公钥，并要求 `verificationMethod` 匹配，不从上传文件动态信任新公钥。

**Q22：你们是否完全实现了 W3C VC 标准？**  
A：我们实现了一个明确版本的 JSON VC 数据结构、Schema、Ed25519 签名、状态端点和账本证据字段，目标是工程互操作原型。它不是完整的跨机构信任注册表，也没有实现所有标准套件或 BBS+ 派生凭证，因此不声称覆盖完整生态。

**Q23：链不可用时能否离线验真？**  
A：签名和文件 Schema 可以离线检查，但“当前仍然有效”无法确认，因为撤销和取代状态可能已经变化。可将结果标为“签名有效、实时状态未知”，不能直接显示“当前有效”。

### 13.6 测试、性能与故障

**Q24：120 个测试具体测了什么？**  
A：shared 33 项覆盖 Schema、CSV、规范化和 VC；chaincode 20 项覆盖角色、状态机、私有承诺、原子批量、申诉和披露；API 67 项覆盖路由、会话、CSRF、Gateway 编排、VC 导出与验证。数量只是规模，更关键的是有职责分离、原子回滚、撤销/取代和篡改等负向用例。

**Q25：为什么性能实验是 84 个单元？**  
A：7 类负载乘 4 档并发乘 3 次重复，即 84。每个单元有 10 秒预热和 30 秒正式采样。不能表述成“7 个并发档位 × 4 个场景”。

**Q26：752 次/秒是否代表学校生产环境容量？**  
A：不代表。它是 WSL 单机回环环境下 `student-private` 在并发 20 的最高中位逻辑操作吞吐，受共享宿主、单 Orderer 和本地网络影响。它用于比较负载形态和识别瓶颈，不用于生产容量承诺。

**Q27：为什么写入负载在某些低并发点反而更慢？**  
A：观察与单 Orderer 的 2 秒 BatchTimeout、闭环 worker 和成块节奏一致，但没有做单独消融，因此这是合理解释而非已经证明的因果结论。后续可固定其他条件，分别改变 BatchTimeout 和批次配置验证。

**Q28：如何定义“故障恢复”？**  
A：不是进程重新出现，而是连续三次读写探针成功，并确认双 Peer 高度和区块哈希一致。Org2 Peer、CCaaS、Orderer 的稳定恢复时间分别为 14.030、16.870、22.482 秒。

**Q29：27 条无效交易是不是系统错误？**  
A：正式 84 个性能单元内无效交易为 0。27 条 `MVCC_READ_CONFLICT` 出现在矩阵完成后的故障驱动诊断，区块、交易 ID 和时间戳保留在审计文件中，没有删除或混入合法请求失败率。

### 13.7 安全、部署与产品边界

**Q30：浏览器登录密码和 Fabric 私钥是什么关系？**  
A：浏览器密码只建立短期应用会话，不是 Fabric 私钥。API 按角色选择受保护的 issuer/reviewer/student Gateway 身份，私钥留在服务器运行时目录。链码仍依据实际 Fabric 证书属性决定权限。

**Q31：如果 API 服务器被攻破，系统还安全吗？**  
A：攻击者可能滥用服务器持有的 Gateway 身份，所以生产环境必须使用 HSM、细粒度身份、密钥轮换、审计和限流。链码能阻止跨角色与非法状态操作，但无法消除合法身份私钥被盗的风险。课程原型不应被表述为抵御服务器完全失陷。

**Q32：为什么仓库里没有密码和私钥？**  
A：演示密码、会话密钥、VC 签发私钥和 Fabric 运行证书都在 `.runtime` 或私有环境文件中，提交包明确排除这些路径。`.env.example` 只描述变量名和非敏感示例格式。

**Q33：项目是否使用真实学生成绩？**  
A：没有。实验使用匿名哈希和合成数据；报告和截图经过检查，不含真实姓名、学号成绩、Cookie、密码、主机名或服务器绝对路径。

**Q34：PostgreSQL 在哪里？链上是否是唯一数据源？**  
A：当前核心凭证状态和有效性以 Fabric 为权威来源；课程实现主要通过链上复合索引形成队列。架构上普通数据库可保存可重建的界面索引和非权威缓存，但不能绕过链码直接改变凭证有效状态。

**Q35：系统当前最大的不足是什么？**  
A：一是单 Orderer 不具备写入高可用；二是终端身份仍通过 API 托管 Gateway 证书，未形成学校级证书生命周期；三是有限披露不是零知识证明；四是性能数据来自单机 WSL；五是跨校信任、Schema 注册和撤销治理仍未建立。

### 13.8 Fabric 网络结构与运维

**Q36：Orderer 会执行智能合约或判断成绩是否合法吗？**
A：不会。Peer 在背书阶段模拟链码并形成读写集，Orderer 只对已背书交易排序和组成区块。区块到达 Peer 后，Peer 再验证背书策略与 MVCC 版本并提交。成绩状态是否合法由链码和 Peer 模拟结果决定，不由 Orderer 决定。

**Q37：Org1 和 Org2 在当前项目中分别做什么？**
A：Org1 承载 issuer、reviewer、student 三类应用身份，Gateway 默认连接 Org1 Peer，Org1 隐式私有集合保存成绩详情。Org2 Peer 保存同一通道的公共账本副本，参与链码安装和组织批准，并用于账本一致性及故障恢复核验。当前 Org2 不是业务 reviewer 所属组织。

**Q38：既然有两个组织，为什么背书策略不是 AND？**
A：当前成绩详情写入 Org1 隐式私有集合，Org2 不应得到明文。开发策略 `OR('Org1MSP.peer','Org2MSP.peer')` 允许由持有私有数据的 Org1 完成模拟和背书。它是隐私边界和最小实验拓扑之间的工程选择，但确实不能证明双组织共同背书。生产化应重新设计集合与状态级背书，使多方能共同确认必要承诺而不获得多余明文。

**Q39：独立复核和双组织背书有什么区别？**
A：独立复核是业务层动作：不同 `app.role` 的 reviewer 证书调用 `ApproveCredential`，且身份摘要不能与提交者相同。双组织背书是 Fabric 层策略：要求哪些 MSP 的 Peer 对同一次模拟结果签名。当前实现了前者，没有要求后者。

**Q40：三个登录账号是不是三套 Fabric 节点？**
A：不是。浏览器账号建立 API 会话；API 根据角色选择三套 Org1 客户端 MSP。它们连接同一个 Org1 Peer，但用不同证书给提案签名。节点是 Orderer、两个 Peer 和 CCaaS 进程，用户身份与节点进程不能混为一谈。

**Q41：为什么 API 只连 Org1 Peer，Org2 还有意义吗？**
A：当前业务私有数据属于 Org1，默认入口连接 Org1 最直接。Org2 仍独立验证区块、保存公共账本、参与链码生命周期并提供一致性和恢复证据。不过单入口意味着查询可用性仍依赖 Org1；生产化应配置多 Gateway 入口、故障切换和按组织路由。

**Q42：Docker 故障后运行的还是区块链吗？**
A：是。原生路径直接启动官方 Fabric 2.5.16 的 `orderer` 和 `peer` 二进制，仍然执行 MSP/TLS、链码背书、Raft 排序、区块提交、MVCC 和 PDC。变化的是进程管理方式，不是把账本换成内存模拟。演示账本只用于特定前端开发场景，不能与原生 Fabric 混称。

**Q43：CCaaS 与普通链码容器有什么区别？**
A：普通模式通常由 Peer 通过容器运行时构建和启动链码；CCaaS 的链码包只声明外部服务地址和类型，链码作为独立进程启动，并用 package ID 与 Peer 建立连接。它便于在 Docker 不可用时管理 Node.js 链码，但当前单实例 9999 也是一个故障点。

**Q44：链码为什么要在两个 Peer 安装并由两个组织批准？**
A：安装让每个 Peer 识别同一 package ID；组织批准表示每个通道成员认可名称、版本、序号和策略；提交 definition 后通道才可调用该链码。当前脚本在两 Peer 安装、两组织批准，然后在提交时同时指定两个 Peer，保证生命周期配置一致。它不意味着普通业务交易必须得到两个 Peer 背书，后者由 signature policy 决定。

**Q45：`version=0.9` 和 `sequence=1` 分别是什么？**
A：version 是团队定义的链码版本标签；sequence 是 Fabric 用于控制定义升级次序的单调递增整数。升级实现或策略时应提交新的定义并增加 sequence，不能只改 version 而保持旧 sequence 反复覆盖。

**Q46：一次查询和一次写交易在网络路径上有什么不同？**
A：查询通过 `evaluateTransaction` 在目标 Peer 本地模拟并返回，不经过 Orderer，也不形成区块。写操作通过 `submit` 完成提案、背书、排序、区块分发、验证和提交，并等待 commit status。Orderer 故障时已有状态可能还能查询，但不能形成新的有效写入。

**Q47：Org2 为什么看不到成绩却能验证区块？**
A：Org2 获得公共写集和私有数据哈希，可以验证公共状态转换、背书和该私有数据对应的哈希承诺，但不是 Org1 隐式集合成员，因此不获得成绩明文。这正是 PDC 将“账本一致性”和“明文可见性”分开的方式。

**Q48：如何证明两个 Peer 的账本一致？**
A：`ledger-info.sh` 分别连接 7051 和 9051 调用 `peer channel getinfo`，比较高度、当前区块哈希和前一区块哈希；三项完全一致才输出 `consistent=true`。故障基准还要求连续三次读写成功后再检查一致性，不能只看进程 PID 或端口。

**Q49：如果 Org1 Peer 宕机，API 会自动切换到 Org2 吗？**
A：当前不会。`fabric-config.ts` 配置的是单个 `peerEndpoint`，角色连接都缓存到该入口。Org2 能继续保存和同步公共账本，但当前应用没有多端点重试和私有数据路由。增加多 Gateway 连接、健康检查和按数据所属组织切换是生产化任务。

**Q50：网络脚本如何防止误删服务器其他目录？**
A：运行数据固定在项目的 `.runtime/native-fabric`。`reset` 在删除前用 `readlink -f` 校验解析后的路径必须精确等于该目录；备份根目录也限制在用户授权路径下。恢复不是覆盖删除，而是把原运行目录移动到带 UTC 时间戳的 `pre-restore` 目录，保留人工回退点。

## 16. 现场代码讲解建议

不要连续滚动完整函数。每次只打开一个关键方法，按“输入—判断—写入—业务结果”说明。

### 16.1 推荐展示一：网络启动与交易入口

在进入业务链码前，建议先用 60–90 秒展示网络入口：

- `infra/fabric-native/native-network.sh:200–209`：Orderer、两 Peer 的启动和入通道顺序；
- `infra/fabric-native/deploy-chaincode.sh:175–189`：安装、启动 CCaaS、两组织批准、提交 definition；
- `apps/api/src/ledger/fabric-ledger.ts:271–290`：API 按 actor 建立并缓存 Gateway 连接；
- `apps/api/src/ledger/fabric-ledger.ts:320–339`：TLS Peer 连接、证书身份和私钥 signer。

讲解顺序是“网络先启动并加入通道—链码完成生命周期—API 才能取得 contract—业务方法再提交交易”。这比直接从 Vue 页面跳到链码更完整。

### 16.2 推荐展示二：批量原子性

文件：`chaincode/grade-contract/src/grade-contract.ts`  
方法：`CreateCredentialBatch`

重点指出：

1. 74–124 行只验证和构建 `prepared`，不写状态；
2. 129 行取得一次 transaction ID；
3. 141 行以后才开始统一写入；
4. 所有记录共享同一交易号。

### 16.3 推荐展示三：修订切换

文件：`chaincode/grade-contract/src/grade-contract.ts`  
方法：`ApproveCredential`

重点指出：

1. 要求 reviewer 角色；
2. 只允许批准 `PENDING_REVIEW`；
3. 提交人身份摘要不能等于复核人；
4. 前序必须仍为 `ACTIVE`；
5. 同一交易完成旧 `SUPERSEDED` 和新 `ACTIVE`。

### 16.4 推荐展示四：VC 联合验证

文件：`apps/api/src/vc/verifier.ts`  
方法：`verifyCredentialFile`

重点指出最终 `conclusion` 同时依赖：

- `signatureValid`；
- `statusActive`；
- `detailHashMatch`；
- `subjectHashMatch`。

这段代码短、逻辑清楚，很适合回答“你们的 VC 创新在哪里”。

### 16.5 推荐展示五：学生私有查询

文件：`chaincode/grade-contract/src/grade-contract.ts`  
方法：`ReadMyCredentialPrivate`

重点指出证书 `subject.hash` 与链上 `subjectHash` 的比较，以及通过后才调用 `getPrivateData`。这能证明权限不是只靠前端隐藏按钮。

## 17. 当前局限与可检验的下一步

### 17.1 当前局限

1. 当前单 Orderer 可恢复但不具备写入高可用；
2. 基准在 WSL 单机回环环境执行，不能外推生产容量；
3. API 托管角色证书，尚未接入学校统一身份和完整证书生命周期；
4. `subjectHash` 的生产匿名化方案仍需加强，不能简单使用学号裸哈希；
5. 有限披露仍是 bearer capability，不具备不可转让性和零知识性质；
6. VC 信任目前由配置公钥建立，尚未实现跨校信任注册表和 Schema 治理；
7. 当前实验拓扑和数据规模有限，未覆盖长期归档、跨地域网络与灾备切换。

### 17.2 下一步不要只说“继续优化”

| 下一步 | 实验方式 | 成功判据 |
| --- | --- | --- |
| Orderer 高可用 | 部署 3 节点 Raft，逐一停止 leader/follower | 单节点故障期间已提交写入不中断，账本最终一致 |
| 主体匿名化 | 对比裸哈希、带域 HMAC、随机化 DID | 公共标识无法通过学号空间枚举，学生仍可稳定查询本人记录 |
| BBS+ 或 ZK 范围证明 | 增加“成绩≥阈值但不公开分数”的证明 | 验证者得到布尔结论，无法从证明恢复原分数 |
| 跨校 VC 信任 | 两套独立组织和信任注册表互验 | 未注册 issuer 被拒，注册 issuer 的 ACTIVE 凭证通过 |
| 生产化基准 | 独立服务器、跨机 Peer、固定资源配额重复测试 | 报告置信区间、瓶颈和容量边界，不沿用 WSL 数字 |

## 19. 结束陈述参考

> ChainGrade 最终完成的不是一个把成绩写进区块链的表单，而是一套可以被解释和审计的成绩凭证生命周期：教师负责签发，复核员独立确认，学生只能读取自己的私有成绩，验证者默认只看到状态和承诺；出现错误时不覆盖历史，而是通过申诉和新版本完成纠正；导出的 VC 也必须结合链上实时状态和详情锚定验证。测试和故障实验说明这些机制在当前课程环境中能够运行，同时我们明确保留了单 Orderer、单机基准、主体匿名化和零知识披露等边界。这个项目的价值不在于使用了多少区块链术语，而在于把“谁负责、谁能看、如何纠错、如何证明”落实成了可以执行和验证的代码规则。
