# 课程答辩 PPT V4 设计说明

## 1. 重构目标

本次重构保留原稿的纸张质感、蓝绿色水彩和技术草图视觉，但将内容逻辑置于视觉之前。课程答辩与竞赛仍然是同一个 ChainGrade 项目；PPT 不另造一套实现，也不使用实验报告之外的新术语或数据。

旧版把七阶段迭代作为主体，容易让时间线遮蔽技术因果。V4 将七阶段压缩为一页能力演进图，主体改为回答数据与隐私、身份与状态、修订与原子性、角色交互、VC 与互操作五组技术问题。

## 2. 章节结构

全稿 25 页，并为每个一级章节设置独立封面：

1. 问题与设计原则：项目定位、三个核心矛盾、四条设计原则。
2. 系统设计与能力演进：架构、能力演进、数据模型、身份权限、状态机、修订、批量、角色交互和 VC。
3. 实验验证与工程证据：实验方法、功能验收、性能测试和故障恢复。
4. 局限、贡献与下一步：项目亮点、贡献比例、局限、演进路线和总结。

页面标题采用“章节眉题 + 2–8 字主题 + 一句结论”的三级体系。章节封面只导航，普通内容页不再以长句充当主标题。

## 3. 核心论证

PPT 围绕三个矛盾建立因果链：

- 单点管理方便但可信不足：以 Fabric 属性身份、独立复核、状态机和历史记录约束职责。
- 成绩需要验证但属于低熵敏感数据：以随机盐、canonical JSON、公共 detailHash 和私有集合降低公开泄露与枚举风险。
- 区块链不可篡改但成绩必须纠错：以旧版本 `SUPERSEDED`、新版本 `ACTIVE`、`previousCredentialId` 和再次独立复核实现不覆盖历史的修订。

申诉接受只开放后续修订入口，不直接改分；批量提交由 `CreateCredentialBatch` 在一次 Fabric transaction 内整批成功或整批失败；VC 可信性由 Schema、Issuer Trust、Signature、Status/Expiry 和 Ledger Anchor 五层共同决定。

## 4. 数据口径

- benchmark：7 类负载 × 4 档并发 × 3 轮，共 84 个合法负载单元。
- C20 公开验证：746.614 req/s，P95 38.202 ms。
- C20 学生私有查询：752.360 req/s，P95 38.096 ms。
- 批量 50 条：482.549 entries/s，P95 2497.371 ms。
- Org2 Peer、CCaaS、单 Orderer 恢复：14.030 s、16.870 s、22.482 s。
- 完整账本审计：高度 12 → 4315，有效交易 32527、无效交易 27、未知原因 0。

上述数字分别回查 `manifest.json`、`ledger-audit.json`、基准摘要和原生 Fabric 端到端恢复报告。单 Orderer 只表述为“可恢复”，不表述为高可用。

## 5. 视觉与演讲设计

- 章节封面使用大号编号和低密度水彩草图，明显区别于内容页。
- 技术证据页减弱装饰，让状态机、表格、数据和结论成为中心。
- 角色交互与 VC 页仅使用项目真实、无 DevTools 覆盖的 UI 截图。
- 代码只保留 `app.role`、`subject.hash` 等决定可信边界的关键行。
- 25 页均内置 Speaker Notes；章节页一句转场，内容页按背景、设计、实现、证据和转场讲述。

## 6. 最终主张

ChainGrade 的重点不是把成绩“存进区块链”，而是让一条成绩能够可信地解释：谁签发、谁复核、谁能看、如何纠错、如何验证，以及系统故障后是否仍然一致。
